# fastnote 附件本地全量与生命周期技术方案

> 2026-07-31 决策修订：附件存储目标改为“引用索引本地全量、Blob 按需缓存”。远端 note 下载和 Realtime 更新只建立 `remote_only` 引用，不再批量下载 Blob；图片随编辑器打开自动缓存，非图片附件点击后缓存。同一远程附件下载请求合并，客户端全局最多并发 3 个。本文中 A1 全量水合、`attachmentsHydrated` 和首次全量离线提示等旧设计均由本修订替代。

- 输出日期：2026-07-30
- 输出文件：`docs/功能拆分与技术方案/fastnote-功能拆分与技术方案-附件本地全量与生命周期-2026-07-30.md`

- 不在范围：公开访客离线附件、独立服务端附件实体、跨用户共享、端到端加密、断点续传

## 2. 模块目标与现状

- 业务目标：保持 Dexie 为即时真相源。设备完成一次成功的“笔记 + 附件”同步后，即使离线也能打开该用户全部私有笔记及其有效附件；删除附件和永久删除笔记时，服务器与本地资源均可重试地最终回收。
- 当前状态：部分支持。
- 关键证据：
  - `E1` [`fastnote/src/shared/lib/storage/dexie.ts:7`]：当前 `note_files` 以 hash 保存本地原始文件，没有 `(noteId, remoteFilename) -> hash` 映射。
  - `E2` [`fastnote/src/features/note-editor/model/use-note-editor.ts:122`]：服务端文件名引用仍通过远端 URL 加载，不会写回 IndexedDB。
  - `E3` [`fastnote/src/entities/note/model/note-sync-service.ts:64`]：上传同步已能根据正文引用构造远端完整文件列表。
  - `E4` [`fastnote/src/entities/note/model/use-note-files.ts:83`]：本地清理函数已存在，但调用者必须提供全库引用，且当前没有接入。
  - `E5` [`fastnote/src/entities/note/model/note-sync-plan-service.ts:37`]：超期删除会先安排 `deleteLocal`，失败后存在失去重试依据的风险。
- 已知缺口：附件未全量本地化；远端文件名无法命中本地 blob；下载任务不可恢复；永久删除不是远端优先；缺少远端硬删除传播；缺少存储配额门禁和完整性审计。

### 2.1 设计前提

1. 每个登录用户使用独立 Dexie 数据库，客户端最终持有该用户全部私有 notes 和所有有效附件 blob。
2. `notes.content` 是附件引用的业务事实源；`notes.files` 是 PocketBase 物理文件集合。
3. 服务器附件继续使用 `notes.files` 多文件字段，不新增 collection 或自定义接口。
4. 正常附件删除服从当前 `updated` 最后写入者获胜规则；不在本方案中引入协作合并。
5. “同步成功”拆为 `notesSynced` 与 `attachmentsHydrated`；只有二者均完成才声明本地全量就绪。

### 2.2 核心不变量

- I1：正文中的本地 hash 引用必须能在 `note_files` 找到 blob，否则该 note 处于 `local_missing`。
- I2：正文中的远端文件名引用必须存在一条 `note_file_refs`，且 `ready` 状态必须关联一个本地 blob。
- I3：远端更新时，提交的 `files` 必须是获胜正文仍引用的完整远端文件集合，新上传 File 除外。
- I4：服务端成功响应前，不删除对应远端映射；本地 blob 只有在远端变更已成功提交，并且全库 note、ref、草稿和任务均无引用后才能删除。
- I5：软删除 note 在 30 天保留期内继续持有附件引用；永久删除必须先完成远端硬删除，再提交本地物理删除。

### 2.3 目标数据流

```text
本地编辑/粘贴/拖放
  -> blob 按 SHA-256 写 note_files
  -> content 写 hash
  -> note 本地保存
  -> note 同步上传/更新（正文 + 完整 files）
  -> PocketBase 返回最终文件名列表
  -> 更新 content、note.files、note_file_refs
  -> 已有 blob 直接标记 ready

远端 note 下载/Realtime 获胜
  -> note 落本地
  -> 解析 content + note.files
  -> 建立 pending_download refs
  -> 有界并发下载 blob
  -> 计算 SHA-256，写 note_files
  -> ref 标记 ready
  -> 全量附件状态 ready

附件节点删除
  -> 新正文先本地保存
  -> 同步提交正文 + 保留 files
  -> PocketBase 删除差集物理文件
  -> 成功响应后移除本地 ref
  -> 空闲期 GC 删除全库无引用 blob
```

## 3. 逐功能点方案

### 3.1 A1 远端附件全量水合

#### 3.1.1 目标与边界

- 用户场景：用户在新设备登录或其他设备新增附件后，本设备完成同步即可离线打开附件。
- 范围内：私有 note 下载、Realtime 更新后的附件下载；断点式任务恢复；下载完成度。
- 范围外：公开访客附件缓存、HTTP Range 断点续传。

#### 3.1.2 现状证据

- 代码事实：
  - `E2` [`fastnote/src/features/note-editor/model/use-note-editor.ts:122`]：远端文件名只生成 URL 返回给视图。
  - `E6` [`fastnote/src/shared/api/pocketbase/files.ts:91`]：现有 API 已能按 noteId/filename 生成文件 URL，但没有下载并持久化方法。
  - `E7` [`fastnote/src/shared/api/pocketbase/realtime-service.ts:92`]：Realtime 只更新 note。
- 现状结论：本地只全量持有由当前设备插入的 blob，远端附件不是本地全量。
- 已确认决策：不新增账号附件总量限制，也不新增本方案自定义的单文件软门禁；继续服从 PocketBase 现有文件字段约束。浏览器 IndexedDB 仍受设备物理容量限制，容量不足作为可恢复同步错误处理。

#### 3.1.3 技术方案

- 方案摘要：note 冲突裁决完成后，根据获胜 note 的正文与 `files` 对账，持久化下载状态并由独立 worker 水合所有有效附件。
- 架构落点：
  - UI：用户资料/同步区域仅展示“附件同步中、已完成、空间不足、部分失败”状态，不阻塞笔记文本浏览。
  - 编排：新增 `processes/sync-notes/model/attachment-hydration-service.ts`；同步和 Realtime 统一调用 `reconcileNoteAttachments(note)`，worker 默认并发 3。
  - 领域：新增 `entities/attachment`，封装引用解析、下载状态、hash 去重和完整性查询。
  - 持久化：`note_file_refs` 保存可恢复下载状态；`note_files` 保存全量 blob。
  - 云端：在 `shared/api/pocketbase/files.ts` 增加 `downloadNoteFile(noteId, filename)`，返回 `File` 或 Blob 元数据；继续使用标准文件 URL。
  - 路由：无变更。
- 数据契约变更：
  - `NoteFile` 增加 `lastReferencedAt`、`downloadedAt?`。
  - 新增 `NoteFileRef`，字段为 `noteId`、`remoteFilename`、`hash?`、`status`、`attempts`、`nextRetryAt?`、`lastError?`、`created`、`updated`。
  - 状态枚举：`pending_download | downloading | ready | missing | failed`；启动时把遗留 `downloading` 复位为 `pending_download`。
- 同步与冲突策略：只水合 note 冲突裁决后的获胜版本；新远端版本移除旧 ref 后再建立新 ref；下载任务不影响 note 游标推进，因为 ref 本身持久化了待办。
- 错误处理与回滚：指数退避，404 标记 `missing`，401 暂停到鉴权恢复，配额错误停止新下载但不清理已有有效 blob。关闭 hydration 开关即可回滚，不删除新表。

#### 3.1.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A1-1 | 增加远端附件下载 API | `fastnote/src/shared/api/pocketbase/files.ts` | 无 | 鉴权与大文件内存占用 |
| T-A1-2 | 实现附件水合 worker 和重试 | `fastnote/src/processes/sync-notes/model/attachment-hydration-service.ts` | A2 | 队列重复执行 |
| T-A1-3 | note 下载/Realtime 后接入引用对账 | `note-sync-executor-service.ts`、`realtime-service.ts` | T-A1-2 | 重复下载 |
| T-A1-4 | 增加同步完成度状态 | `sync-status-state.ts`、用户同步 UI | T-A1-2 | 状态文案误导 |

#### 3.1.5 验收标准

- AC-A1-1：新设备初次同步完成后断网，所有私有 note 的有效附件均能打开。
- AC-A1-2：下载中关闭应用，再次启动后任务从持久化状态继续，不要求重新拉取 note。
- AC-A1-3：相同字节的多个附件只在 `note_files` 保存一个 blob，但每个远端 note 文件保留独立 ref。

#### 3.1.6 测试与验证

- 单元测试：引用对账、状态恢复、重试退避、hash 去重、404/401/quota 分类。
- 集成/冒烟：设备 A 上传多个格式 -> 设备 B 登录同步 -> 断网打开图片/PDF/压缩包。
- 回归关注点：公开只读路由不触发私有附件全量下载；guest 数据仍保持本地可用。

#### 3.1.7 风险与未决问题

- 风险：大文件 `arrayBuffer()` 计算 hash 会产生峰值内存。
- 已确认决策：首次全量不阻塞文本笔记使用；应用分别展示“笔记已同步”和“附件同步中 x/y”，附件全部 ready 后提示一次“附件已全部离线可用”。

### 3.2 A2 本地附件引用索引

#### 3.2.1 目标与边界

- 用户场景：无论正文保存的是本地 hash 还是 PocketBase 文件名，编辑器都优先读取本地 blob。
- 范围内：Dexie schema、仓储、结构化引用解析、guest 数据迁移。
- 范围外：修改服务器文件字段。

#### 3.2.2 现状证据

- 代码事实：
  - `E1` [`fastnote/src/shared/lib/storage/dexie.ts:7`]：`note_files` 当前仅以 hash 为键。
  - `E8` [`fastnote/src/shared/lib/storage/types.ts:14`]：`NoteFile` 无远端映射或引用时间。
  - `E9` [`fastnote/src/shared/lib/storage/guest-data.ts:35`]：guest 合并已经迁移 note 和 note_files，新表需同步纳入。
  - `E10` [`fastnote/src/entities/note/model/note-sync-service.ts:12`]：正文引用提取仍使用 HTML 正则。
- 现状结论：不能由 `(noteId, remoteFilename)` 找到本地 hash；清理也无法判断 blob 被哪些 note 引用。
- 推断与待确认：同一 hash 可跨 note 复用本地 blob，但 PocketBase 文件仍属于各自 note 记录，不做跨 note 远端去重。

#### 3.2.3 技术方案

- 方案摘要：Dexie 升级到 v4，增加复合主键引用表，以 hash 表保存 blob，以引用表保存 note 归属和远端文件名。
- 架构落点：
  - UI：无直接变更。
  - 编排：会话数据库准备后执行一次幂等附件索引迁移。
  - 领域：`entities/attachment` 暴露 `resolveLocalFile(noteId, url)`、`reconcileRefs(note)`、`collectLiveHashes()`。
  - 持久化：`shared/lib/storage/attachment-files.ts` 封装事务，不让 process 直接操作 Dexie 表。
  - 云端：无 schema 变更。
  - 路由：无变更。
- 数据契约变更：

```ts
interface NoteFile {
  hash: string
  file: File
  fileName: string
  fileSize: number
  fileType: string
  created: string
  updated: string
  lastReferencedAt: string
  downloadedAt?: string
}

interface NoteFileRef {
  noteId: string
  remoteFilename: string
  hash?: string
  status: 'pending_download' | 'downloading' | 'ready' | 'missing' | 'failed'
  attempts: number
  nextRetryAt?: string
  lastError?: string
  created: string
  updated: string
}
```

- Dexie v4：
  - `note_files`: `&hash, fileName, fileSize, fileType, created, updated, lastReferencedAt`
  - `note_file_refs`: `[noteId+remoteFilename], noteId, remoteFilename, hash, status, updated`
- 结构化解析：集中实现 `extractAttachmentReferences(content)`，使用 DOMParser 查询 `file-upload[url]`；编辑器活态优先遍历 Tiptap JSON。删除同步、下载对账和 GC 只能调用该公共能力，不再各写正则。
- 兼容与迁移：旧 `note_files` 保留原 hash 和 blob，`lastReferencedAt` 缺省时以 `updated` 回填；全量扫描本地 notes，为远端文件名建立 pending ref，为 hash 引用刷新 `lastReferencedAt`。
- 错误处理与回滚：v4 只增表/增索引；迁移失败不删除旧数据，附件仍可走现有远端 URL 回退。

#### 3.2.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A2-1 | 定义 NoteFileRef 与 Dexie v4 | `storage/types.ts`、`storage/dexie.ts` | 无 | schema 升级 |
| T-A2-2 | 实现附件引用仓储事务 | `storage/attachment-files.ts` | T-A2-1 | 部分写入 |
| T-A2-3 | 集中结构化引用解析 | `entities/attachment/lib/attachment-references.ts` | 无 | 历史 HTML 兼容 |
| T-A2-4 | 编辑器改成本地优先解析远端文件名 | `features/note-editor/model/use-note-editor.ts` | T-A2-2 | object URL 生命周期 |
| T-A2-5 | guest 合并/清理覆盖新表 | `storage/guest-data.ts` | T-A2-1 | 跨作用域遗漏 |

#### 3.2.5 验收标准

- AC-A2-1：远端 filename 引用在 ref ready 后不发起网络请求即可展示。
- AC-A2-2：数据库升级不丢失任何现有 note_files blob。
- AC-A2-3：两个 note 引用相同 hash 时，删除其中一个引用不会删除共享 blob。

#### 3.2.6 测试与验证

- 单元测试：Dexie v3 -> v4、复合键 CRUD、DOMParser 历史内容、guest 合并。
- 集成/冒烟：升级前插入附件，升级后断网打开；切换两个账号确认附件库隔离。
- 回归关注点：登出不清理其他用户作用域数据库。

#### 3.2.7 风险与未决问题

- 风险：object URL 未释放造成内存泄漏，NodeView 卸载时必须 revoke。
- 未决问题：是否允许用户主动清空本地附件缓存；若允许，状态必须退回 pending_download，而不是删除 ref。

### 3.3 A3 正文引用驱动的远端删除

#### 3.3.1 目标与边界

- 用户场景：用户从富文本删除附件 A，成功同步后服务器物理文件 A 被删除，其他保留附件不受影响。
- 范围内：活跃 note 的附件增删、混合上传与删除、失败重试。
- 范围外：永久删除整个 note（见 A5）。

#### 3.3.2 现状证据

- 代码事实：
  - `E3` [`fastnote/src/entities/note/model/note-sync-service.ts:64`]：同步已经按正文引用构造 `filesForUpload`。
  - `E11` [`fastnote/src/shared/api/pocketbase/notes.ts:58`]：没有新 File 时提交完整文件名数组，有 File 时使用 FormData。
  - `E12` [`fastnote/src/entities/note/model/note-sync-service.ts:160`]：响应成功后回填 `record.files`。
- 现状结论：PocketBase 差集删除的基础已经存在，但没有显式不变量、ref 事务和删除回归测试。
- 推断与待确认：PocketBase `notes.files` 普通赋值是完整替换；被新列表移除的文件由 PocketBase 标准 FileField 物理删除。

#### 3.3.3 技术方案

- 方案摘要：每次远端 note 更新都从获胜正文生成准确的“保留远端文件名 + 新 File”集合，正文和 files 在同一次请求提交；成功响应后再更新本地 refs。
- 架构落点：同步规则留在 `entities/attachment`/`entities/note`，`shared/api` 只负责序列化请求。
- 数据契约变更：不改 PocketBase schema；`Note.files` 继续保存服务器返回的最终文件名数组。
- 同步与冲突策略：
  - 本地 note 获胜：按其正文提交完整 files，删除差集。
  - 远端 note 获胜：不得执行本地计算出的删除，改为下载并对账远端版本。
  - 混合新增/删除：保留文件名和 File 一起提交，返回后以 `record.files` 为准。
  - 正文无附件：必须显式发送 `files: []`，不依赖本地旧 `Note.files`。
- 错误处理与回滚：请求失败时保留旧 ref/blob，note 变更继续由现有增量同步重试；禁止在请求前运行 GC。

#### 3.3.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A3-1 | 以公共解析器替换同步正则 | `note-sync-service.ts` | A2 | 历史内容误判 |
| T-A3-2 | 明确空附件 payload 与完整替换语义 | `notes.ts` | T-A3-1 | 误清空 |
| T-A3-3 | 成功响应后事务化 reconcile refs | `note-sync-service.ts`、附件仓储 | A2 | 响应中断 |
| T-A3-4 | 补删除、混合增删和失败重试测试 | `tests/integration/sync` | 上述任务 | mock 与真实 PB 差异 |

#### 3.3.5 验收标准

- AC-A3-1：A/B 两附件中删除 A 后，服务器 `files` 只剩 B，A URL 返回 404，B 正常。
- AC-A3-2：删除最后一个附件后服务器 `files=[]`。
- AC-A3-3：同步失败时服务器与本地旧 ref/blob 保持不变；重试成功后再清理。

#### 3.3.6 测试与验证

- 单元测试：引用集合差集、空数组 payload、重复引用去重。
- 集成/冒烟：真实 PocketBase 上传 A/B -> 删除 A -> 同步 -> 检查记录与物理 URL。
- 回归关注点：只修改正文文本不能重复上传附件。

#### 3.3.7 风险与未决问题

- 风险：新文件上传仍需要服务端生成文件名后第二次回填正文，Realtime 可能短暂看到中间内容；本方案先保持兼容。
- 未决问题：是否在后续单独治理上传中间态，不作为附件删除上线阻塞项。

### 3.4 A4 本地安全 GC

#### 3.4.1 目标与边界

- 用户场景：附件删除并同步成功后，本地不无限积累无引用 blob，也不会破坏撤销、软删除恢复或跨 note hash 复用。
- 范围内：全库引用扫描、远端成功门禁、GC 事务、审计模式。
- 范围外：操作系统级磁盘清理。

#### 3.4.2 现状证据

- 代码事实：`E4` [`fastnote/src/entities/note/model/use-note-files.ts:83`] 会把调用者未传入的所有 hash 视为可删除，当前没有全库引用与远端成功门禁。
- 现状结论：该函数不能直接用于单 note 保存，必须改造成全库 GC 服务。
- 已确认决策：30 天是回收站 note 的保留期，不是无引用 blob 的额外 GC 计时器。回收站 note 在 30 天内仍进入 live set；普通附件从正文移除后，必须等远端更新成功且全库无引用，之后可在空闲期 GC，不再额外等待 7 天或 30 天。

#### 3.4.3 技术方案

- 方案摘要：GC 只在成功同步后或启动空闲期运行，先构造 live set，再删除超期孤儿。
- live set 包含：所有本地 notes（含 30 天内软删除）的 hash 引用；所有 ready/pending ref 的 hash；正在上传/下载的任务；未保存编辑草稿引用。
- `note_files.lastReferencedAt` 在每次全量扫描时刷新，用于审计和问题定位。只有 `hash ∉ liveSet` 且关联远端变更已成功提交时才进入待删除集合；GC 在空闲期按批次执行。
- 先提供 audit-only 报告，灰度确认后启用实际删除；每批最多 100 个，事务提交并记录计数。
- 配额不足时不得跳过不变量直接删除有效附件；只允许优先清理已经满足 GC 条件的孤儿。

#### 3.4.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A4-1 | 实现全库 live hash 收集 | `entities/attachment/model/attachment-gc-service.ts` | A2 | 漏算草稿 |
| T-A4-2 | 增加 audit-only 与宽限删除 | 同上、storage repository | T-A4-1 | 误删不可恢复 |
| T-A4-3 | 同步成功/启动空闲接入 GC | `processes/sync-notes`、session | T-A4-2 | 启动性能 |

#### 3.4.5 验收标准

- AC-A4-1：共享 hash 被至少一个 note/ref 引用时永不删除。
- AC-A4-2：刚从正文删除但尚未成功同步的 blob 保留；处于 30 天回收站保留期的 note 附件也必须保留。
- AC-A4-3：远端变更成功且全库无引用的 blob 在下一次空闲 GC 中被清理，ref 和 note 不受影响。

#### 3.4.6 测试与验证

- 单元测试：live set、软删除保留、共享 hash、草稿、任务状态、时间边界。
- 集成/冒烟：删除附件后断网 -> 本地保留 -> 恢复网络并同步成功 -> 空闲 GC；软删除 note 在第 29/30/31 天的附件保留与永久清理链路。
- 回归关注点：guest 数据合并过程中禁止 GC。

#### 3.4.7 风险与未决问题

- 风险：未保存草稿没有持久化引用时可能漏算；编辑器打开期间应暂停删除或注册草稿引用 provider。
- 已确认决策：不增加无引用 blob 宽限期；30 天仅用于软删除 note 的恢复窗口。

### 3.5 A5 永久删除远端优先

#### 3.5.1 目标与边界

- 用户场景：用户点击永久删除或软删除超过 30 天后，服务器 note 与其所有物理附件先被删除，随后本地数据释放；失败可重试。
- 范围内：私有 note 硬删除、持久化 purge 任务、404 幂等成功。
- 范围外：文件夹子树永久删除的业务拆分细节。

#### 3.5.2 现状证据

- 代码事实：
  - `E13` [`fastnote/src/features/note-actions-menu/model/use-note-actions-menu.ts:40`]：永久删除只把 `updated` 写为 1970。
  - `E14` [`fastnote/src/entities/note/model/note-sync-plan-service.ts:37`]：计划先 `deleteLocal` 再远端 `delete`。
  - `E15` [`fastnote/src/entities/note/model/note-sync-executor-service.ts:57`]：执行器会立即删除本地 note，远端动作只是更新软删除 note。
- 现状结论：1970 时间不会进入 `updated > cursor` 的正常增量集合；即使进入，远端文件仍可能保留且失败后缺少重试依据。
- 推断与待确认：PocketBase 删除 note 记录会由标准 FileField 删除该记录目录下的附件。

#### 3.5.3 技术方案

- 方案摘要：新增本地持久化 `note_purge_jobs`，永久删除操作在 Dexie 事务中写 job 并隐藏 note；同步每次独立于游标先排空 purge job。
- 数据契约：

```ts
interface NotePurgeJob {
  noteId: string
  status: 'pending' | 'running' | 'failed'
  attempts: number
  nextRetryAt?: string
  lastError?: string
  created: string
  updated: string
}
```

- Dexie v4：`note_purge_jobs: '&noteId, status, nextRetryAt, updated'`。
- 云端：`notesService.deleteNote(noteId)` 调用 `pb.collection('notes').delete(noteId)`；404 视为幂等成功。
- 执行顺序：创建 job -> UI 隐藏 -> 远端 delete -> Dexie 事务删除 local note、该 note refs 和 job -> 触发 GC。
- 远端硬删除传播：A6 的全量远端 ID 清单用于让离线设备识别“已同步过但远端缺失”的 note；本地未上传 note 通过缺少 `user_id` 区分，不会误删。
- 错误处理：网络/5xx 指数退避且保留 job/note；鉴权失败暂停；404 继续本地提交；不得回到“先删本地”。

#### 3.5.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A5-1 | 增加 purge job 表和仓储 | `storage/dexie.ts`、新 repository | A2 | 事务迁移 |
| T-A5-2 | 永久删除动作改写 job | `use-note-actions-menu.ts` | T-A5-1 | UI 状态 |
| T-A5-3 | 增加 PB 标准 record delete | `notes.ts`、`note-remote-service.ts` | 无 | 404/权限 |
| T-A5-4 | 同步前执行远端优先 purge | `sync-orchestrator-service.ts` | T-A5-1/3 | 顺序错误 |
| T-A5-5 | 30 天超期删除复用 purge | sync plan/domain rules | T-A5-4 | 恢复窗口 |

#### 3.5.5 验收标准

- AC-A5-1：离线点击永久删除后 note 不再展示，但 job 和 note 仍在 IndexedDB，联网后自动完成。
- AC-A5-2：远端删除失败时本地依据不丢；重启后继续重试。
- AC-A5-3：远端成功后 note 记录和附件 URL 均不存在，本地 note/ref/job 删除。

#### 3.5.6 测试与验证

- 单元测试：job 状态机、404 幂等、重试、远端成功前本地保留。
- 集成/冒烟：上传附件 note -> 离线永久删除 -> 重启 -> 联网 -> 验证 PB record/URL 和 IndexedDB。
- 回归关注点：软删除恢复不创建 purge job；文件夹子树不能部分成功后无记录。

#### 3.5.7 风险与未决问题

- 已确认决策：本方案不增加旧客户端兼容门禁或最低版本判断，只保证新实现客户端之间的删除与同步语义。
- 未决问题：文件夹永久删除采用逐 note job 还是子树批次 job；建议独立任务设计，不在本模块默认实现。

### 3.6 A6 全量远端 ID 清单与修复

#### 3.6.1 目标与边界

- 用户场景：客户端错过 Realtime delete 或附件下载中断后，下一次同步仍能自动恢复完整状态。
- 范围内：轻量远端 manifest、硬删除传播、附件一致性审计。
- 范围外：服务端校验任务。

#### 3.6.2 现状证据

- 代码事实：`E16` [`fastnote/src/processes/sync-notes/model/sync-orchestrator-service.ts:9`] 当前两端都只读取游标后的增量，远端列表缺失不能被解释为删除。
- 现状结论：要使用 PocketBase record 硬删除，前端必须额外获得完整远端 ID 集合。
- 推断与待确认：notes 数量显著大于附件数量时，manifest 只取 `id,updated` 可将开销控制在可接受范围。

#### 3.6.3 技术方案

- 每次会话首次同步和每日维护同步拉取当前用户完整 `id,updated` manifest；普通频繁保存仍走增量。
- 若本地 note 有远端归属标记、没有 pending purge 且不在 manifest：视为远端硬删除，删除本地 note/ref；未上传 note 不受影响。
- 附件审计分类：`ready`、`pending_download`、`local_missing`、`remote_extra`、`remote_missing`。
- 修复策略：local missing 重新下载；pending 重试；remote extra 在拥有该 note 的下一次维护更新中提交准确 files；remote missing 只标错并提示，不静默删除正文节点。
- 远端 manifest 拉取失败时不执行任何基于“缺失”的删除。

#### 3.6.4 实施任务拆分

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A6-1 | 增加轻量 note manifest API | `shared/api/pocketbase/notes.ts` | 无 | 大账号分页 |
| T-A6-2 | 维护同步传播硬删除 | `sync-maintenance-service.ts` | A5 | 误判缺失 |
| T-A6-3 | 附件完整性审计与修复 | `entities/attachment/model` | A1/A2 | 自动修复副作用 |

#### 3.6.5 验收标准

- AC-A6-1：设备离线期间另一设备硬删除 note，重新上线执行维护同步后本地删除。
- AC-A6-2：manifest 请求失败时不删除任何本地 note。
- AC-A6-3：手工删除本地 blob 后，下一次维护同步自动重新下载。

#### 3.6.6 测试与验证

- 单元测试：manifest 差集、未上传 note 排除、请求失败保护、五类审计结果。
- 集成/冒烟：关闭 Realtime 后远端硬删除，再执行维护同步。
- 回归关注点：增量游标语义保持不变，manifest 不写游标。

#### 3.6.7 风险与未决问题

- 风险：账号 note 数量极大时 manifest 成本上升；可按日运行并只选两个字段。
- 未决问题：维护同步周期，建议会话首次 + 每 24 小时一次。

### 3.7 A7 配额、持久化与可观测性

#### 3.7.1 目标与边界

- 用户场景：用户能知道附件是否真正全量落本地，空间不足时不会得到虚假的成功状态。
- 范围内：Storage API、状态统计、错误分类、用户可见状态。
- 范围外：购买云空间和系统磁盘管理。

#### 3.7.2 现状证据

- 代码事实：`E8` [`fastnote/src/shared/lib/storage/types.ts:14`] 当前附件模型没有水合状态、配额或完整性字段。
- 现状结论：无法区分“note 已同步”和“附件可离线”。
- 推断与待确认：浏览器可能驱逐非持久 IndexedDB；Tauri/WebView 的实际配额需分别验证。

#### 3.7.3 技术方案

- 首次启用全量附件时调用 `navigator.storage.persist()`，并使用 `estimate()` 做下载前后统计；不根据统计值实施账号总量限制。
- 状态输出：总附件数、ready/pending/failed/missing、已用字节、预计总字节、persistent 是否授予。
- `attachmentsHydrated=false` 时不得展示“同步全部完成”；允许文本笔记继续使用。
- 提示规则：同步区域显示“附件同步中 x/y”；离线时显示“等待网络”；首次全量 ready 后仅提示一次“附件已全部离线可用”，后续成功不重复打扰。
- 失败规则：下载失败或配额不足时保留可见状态和“重试”操作；空间不足文案为“设备存储空间不足，笔记已同步，仍有 N 个附件未下载”。暂停队列并保留 pending ref，禁止自动淘汰仍被引用 blob。
- 记录结构化日志：download success/failure、remote prune、local GC、purge、repair。

| 任务ID | 任务描述 | 变更文件 | 依赖 | 风险 |
| ------ | -------- | -------- | ---- | ---- |
| T-A7-1 | Storage persist/estimate adapter | `shared/lib/storage` | 无 | 浏览器差异 |
| T-A7-2 | 附件同步状态聚合 | `processes/sync-notes/model` | A1/A2 | 统计开销 |
| T-A7-3 | 用户同步区域展示状态 | `widgets/user-profile` | T-A7-2 | 信息密度 |

#### 3.7.5 验收标准

- AC-A7-1：空间不足时 note 文本同步成功，但附件状态明确失败且任务可重试。
- AC-A7-2：只有所有有效附件 ready 后才显示“附件已全部离线可用”。
- AC-A7-3：清理孤儿后容量统计更新，不能把有效附件计入已清理。

#### 3.7.6 测试与验证

- 单元测试：Storage API 不可用、拒绝 persist、quota exceeded、状态聚合。
- 集成/冒烟：模拟低配额并恢复空间后继续下载。
- 回归关注点：不支持 Storage API 的平台降级为 unknown，不阻断本地笔记编辑。

#### 3.7.7 风险与未决问题

- 风险：浏览器持久存储授权不是绝对保证，产品文案不能承诺操作系统永不清理。
- 已确认决策：不设置账号附件总量软门禁；同步状态放在现有用户同步区域，错误时提供重试，不使用阻塞式弹窗。

1. 先实现 A2 数据结构和解析器，所有删除逻辑保持关闭。
