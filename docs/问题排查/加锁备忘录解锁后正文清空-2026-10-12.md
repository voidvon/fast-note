# 加锁备忘录解锁后正文清空

## 结论与证据边界

本地已稳定复现解锁与同步交错导致旧空正文覆盖编辑器的竞态，并完成修复。此次没有读取线上账号、备忘录或运行日志，因此不能把本地复现直接认定为线上这次数据丢失的唯一原因。改动尚未部署，也不会恢复已经被覆盖的正文。

## 可复现的问题

1. **密码校验期间正文快照过期。** 详情页在校验之前读取本地笔记；校验全局 PIN 可能等待云端配置。期间同步将本地记录替换成有正文的新记录，校验成功回调仍将校验前的空记录写入编辑器。新增集成测试在修复前得到 `''`，预期为同步后的正文。
2. **迟到的解锁响应影响下一次选择。** 校验开始后切换到另一篇笔记，原请求返回时仍触发 `onUnlocked`，将旧空正文写入下一篇的编辑器。新增集成测试在修复前稳定失败。
3. **空正文格式差异触发误保存。** 存储中的 `''` 经 Tiptap 加载后变为 `<p></p>`。原保存流程只比较内容字符串，未确认正文加载完成或编辑器发生了修改。如果同步随后补齐存储正文，未修改的空编辑器失焦就可能覆盖这篇笔记。真实 Tiptap 测试确认了这种序列化差异。

## 修复行为

- 解锁成功后重新读取最新本地正文，再填入编辑器。
- 锁状态查询、PIN 和生物识别解锁使用请求版本，取消过期结果；回调在等待编辑器挂载后再次校验版本。
- 切换笔记和卸载详情页时取消待处理操作。即使切走后重新选回同一篇，也不会复用原解锁请求。
- 加锁笔记的会话状态确定之前保持锁定视图。
- 所有保存入口核对编辑器已成功加载的笔记 ID，未加载正文时仅允许已有本地状态落盘。
- 编辑器记录加载后的标准化正文和后续修改。未修改的编辑器不会回写；主动清空正文、编辑后恢复原文均仍可保存。自动锁定和锁设置的强制保存也遵守该保护。
- 若未修改的编辑器快照与最新存储正文冲突，设置锁时保留最新记录并提示尚未完成保存。

- Cypress：`tests/e2e/locked-note-home-restore.cy.ts` 的 3 个用例通过，使用真实编辑器、密码摘要和 IndexedDB，覆盖桌面首页默认笔记解锁后的失焦/离开/刷新、主动清空持久化，以及中间版本保存后恢复原文。
- `npm run build`：前端类型检查、前端构建和后端构建通过。
- 全量 Vitest 和 lint 存在仓库原有失败；使用 HEAD 的独立代码副本和相同依赖对照，确认没有新增失败。原全量测试为 402 通过、62 失败，修改后为 413 通过、61 失败；原有空草稿离开时误保存的用例随本次保护通过。全量 lint 前后均为 106 个错误，变更文件单独 lint 通过。
